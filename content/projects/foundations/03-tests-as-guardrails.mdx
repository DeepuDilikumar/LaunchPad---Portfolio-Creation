<Explain id="intro">
An agent will tell you it's done. Tests are how you find out whether that's true.

In this module you'll make the agent write **failing tests first**, watch them fail for the right reason, and only then let it write the code. It feels slower. It's the single habit that most separates engineers who ship with agents from engineers who get burned by them.
</Explain>

<Explain id="why-red-first">
Why the test has to fail first:

- **A test that never failed proves nothing.** It might not even run.
- **The failure message tells you the test checks what you meant.** "Cannot find module" means it's wired up; "expected false to be true" means it's asserting behaviour.
- **It pins the agent to the spec.** The implementation has to satisfy tests you approved, not tests it wrote afterwards to match its own code.
</Explain>

<Explain id="read-the-tests">
Before you let it implement, read the tests. You're checking intent, not style:

- Does each acceptance criterion have at least one test?
- Do the tests check **behaviour** ("the 4th request is blocked") rather than internals ("the map has 3 entries")?
- Is time injected, so a "refills after 20 seconds" test runs instantly?
- Is there one test for the thing most likely to break? For a rate limiter, that's refill and the cap.
</Explain>

<Pitfall
  id="pitfall-edits-tests"
  title="edits the tests to make them pass"
  recovery={`You changed a test file. Revert every change under test/ with git checkout -- test/. The tests are the spec. Make the implementation pass the original tests. If you believe a test is wrong, explain which assertion and why, and wait for me.`}
>
This is the most common way agents "finish" early. Check with `git diff --stat test/` after every implementation step. Add "never edit tests to make them pass" to your instructions file if it isn't there yet.
</Pitfall>

<Explain id="read-the-diff">
Green tests aren't the end of the review. Read the diff:

```bash
git diff --stat
git diff src/
```

Read it for **intent**: does the code do what the plan said, in the files the plan said? Then look for the things tests rarely catch: a new dependency, a swallowed error, a hard-coded value, a `TODO` it left behind, or code nobody asked for.
</Explain>

<Explain id="take-the-wheel">
Signals that it's time to stop prompting and take the wheel:

- **The same fix three times.** The agent is looping. Read the error yourself.
- **It's making the test weaker** to pass, or adding special cases for test inputs.
- **The diff keeps growing** while the failure stays the same.
- **You can't explain the change** it just made. Don't commit code you can't explain.

Taking the wheel can be small: write the one line yourself, or write a sharper test that pins the bug, then hand it back.
</Explain>

<Decision id="decision-tests" question="Look at the tests the agent wrote. Which one would you have missed, or which did you change, and why?" />

<Interview q="How do you stop an AI agent from writing tests that just confirm its own code?">
I make it write the tests first, from the spec, and run them to see them fail before any implementation exists. I review the tests for behaviour against the acceptance criteria. Then the implementation has to satisfy tests I approved, and I check git diff on the test folder after every step so it can't quietly weaken them. Time and randomness get injected so tests are deterministic.
</Interview>

<Interview q="When do you stop delegating to the agent and write the code yourself?">
When it's looping: the same fix repeatedly, a growing diff with the same failure, or tests getting weaker. Also when I can't explain its last change. Usually taking over is small: I read the actual error, write a sharper failing test or the one tricky line, and hand it back. The goal is to keep the loop moving, not to prove the agent can do everything.
</Interview>
