<Explain id="intro">
Every module in this course runs the same loop: **spec → plan → build → verify → decide**. This module is about the first two steps, because that's where most agent sessions go wrong.

An agent that starts typing straight away will build *something*. Often it's a reasonable answer to a question you didn't ask. A five-minute plan review is the cheapest place to catch that.
</Explain>

<Explain id="what-a-spec-is">
A spec for an agent is short and concrete. It answers four questions:

1. **What are we building?** One paragraph.
2. **What's in and what's out?** The out list matters more. It stops scope creep.
3. **How will we know it works?** Acceptance criteria you could turn into tests.
4. **What are the constraints?** Language, dependencies, performance, things not to touch.

Half a page is plenty. If the spec runs longer, the task is probably two tasks.
</Explain>

<Expect id="spec-example" kind="tree" example>

```md
# shortly — spec

## Goal
A tiny HTTP service that turns long URLs into 6-character codes and redirects.

## In scope
- POST /shorten with a JSON body { "url": "..." } returns 201 and a code
- GET /:code redirects with 301
- Rate limit POST /shorten to 10 requests per minute per IP

## Out of scope
- Accounts, custom codes, analytics, a database (in-memory is fine for now)

## Acceptance criteria
1. Only http and https URLs are accepted; anything else returns 400
2. Codes are 6 characters, [a-zA-Z0-9], and never repeat
3. Unknown codes return 404
4. The 11th POST in a minute from one IP returns 429 with Retry-After
5. The rate limiter is tested without real waiting (inject the clock)

## Constraints
- Node + TypeScript, no web framework, Vitest for tests
- No new dependencies without asking
```

</Expect>

<Explain id="plan-mode">
Now ask for a plan, not code.

- **Claude Code:** press **Shift+Tab** until the footer says plan mode. In plan mode it can read files and think, but it won't edit anything until you approve.
- **Codex:** there's no separate plan switch in every version, so say it in the prompt: plan only, no edits, wait for approval. If your version supports a read-only approval mode, turn it on.
</Explain>

<Explain id="review-checklist">
Review the plan the way a tech lead reviews a design doc. Read it once, then check:

- **Does every acceptance criterion map to a test?** If criterion 4 has no test, it won't be done.
- **Is anything in the plan that's out of scope?** Agents like adding databases, auth and config files.
- **Are the files small and named for what they do?** `utils.ts` is a smell.
- **Did it raise real ambiguities,** or invent answers silently?
- **Is the order sensible?** Pure logic first (store, rate limiter), then the HTTP layer.

Reply with your changes in one message. Then save the agreed plan, so the next session can read it.
</Explain>

<Pitfall
  id="pitfall-overbuilt-plan"
  title="plans a database, a framework and a config system for a 100-line service"
  recovery={`This plan is bigger than the spec. Remove everything that isn't needed for the acceptance criteria in SPEC.md: no database, no web framework, no config library. Keep the data in memory behind a small interface so we can swap it later. Show me the revised plan, still without code.`}
>
Agents pattern-match to "production app" and reach for the full stack. Point it back at the out-of-scope list. The spec is your leverage, which is why you wrote one.
</Pitfall>

<Pitfall
  id="pitfall-starts-coding"
  title="starts writing code before you approved the plan"
  recovery={`Stop. Revert any files you created in this session. I want a plan first, with no edits. Re-read SPEC.md and give me the plan in the format I asked for.`}
>
In Claude Code, check that plan mode is on (Shift+Tab). In Codex, say "don't edit any files until I approve" in the same message as the request.
</Pitfall>

<Callout id="interview-angle" kind="interview">
"Tell me how you work with AI tools" is now a standard interview question. "I write a spec, make it plan first and review the plan before it writes code" is a much stronger answer than "I use Copilot".
</Callout>

<Interview q="Why review an agent's plan instead of just reviewing the code it writes?">
Because a plan is cheap to change and code isn't. Reviewing a plan takes a few minutes and catches the expensive mistakes: wrong scope, wrong architecture, missing requirements. Once a few hundred lines exist, the agent and I both anchor on them, and the review turns into patching. I still review the code, but by then I'm checking execution, not direction.
</Interview>

<Interview q="What makes a spec good enough for an agent to follow?">
It's short, it has an explicit out-of-scope list, and its acceptance criteria are testable: each one could become a test with a clear pass or fail. It names constraints the agent can't infer, like no new dependencies or an injected clock. I keep it under a page; if it grows past that, I split the task.
</Interview>
