<Explain id="intro">
In the next ten minutes you'll install a coding agent, point it at a fresh repo, and write the one file that decides how well it works for you: the instructions file.

You only need one agent. Every prompt in this course has a **Claude Code** version and a **Codex** version. Pick the tool you already pay for, and switch the tabs at the top of the page to match. Your choice is remembered.
</Explain>

<Explain id="what-an-agent-is">
A coding agent is a loop. It reads files, runs commands, edits code, and looks at the result, then decides what to do next. You stay in charge of three things the agent can't do for you:

- **Say what done looks like.** A spec, a test, a number.
- **Approve the plan** before code gets written.
- **Decide** when a change is good enough to keep.

The rest of this course is practice at those three things on systems that are hard enough to matter.
</Explain>

<Explain id="how-agents-read">
When you start a session, the agent knows nothing about your project. It doesn't remember yesterday's session either. Here is what happens instead:

1. It loads an **instructions file** from the repo root: `CLAUDE.md` for Claude Code, `AGENTS.md` for Codex.
2. It explores: lists folders, searches for names, reads the files it thinks matter.
3. Everything it read sits in its **context window**, a fixed budget of text. When the budget fills up, older details get summarised or dropped.

So the instructions file is the agent's memory of your project. It is read at the start of every session, which makes it the highest-leverage file in the repo.
</Explain>

<Expect id="instructions-example" kind="tree" example>

```md
# shortly

A URL shortener with a token-bucket rate limiter. Node + TypeScript, no framework.

## Commands
- pnpm test        run Vitest once
- pnpm typecheck   tsc --noEmit
- pnpm dev         run the server with reload

## Conventions
- Write the failing test first, then the code.
- Keep modules small: src/store.ts, src/rate-limit.ts, src/server.ts.
- Inject the clock (now: () => number) so time-based code is testable.

## Never
- Never add a dependency without asking.
- Never edit tests to make them pass. Fix the code, or tell me the test is wrong.
```

</Expect>

<Pitfall
  id="pitfall-long-instructions"
  title="writes a 200-line instructions file full of generic advice"
  recovery={`Cut the instructions file to under 40 lines. Keep only rules that are specific to this repo and that you would get wrong without being told. Delete generic advice like "write clean code" or "follow best practices". Show me the result before saving.`}
>
Long files dilute the rules that matter, and they cost context on every session. A good test for each line: would the agent do the wrong thing without it? If not, delete it.
</Pitfall>

<Explain id="both-files">
If you use both tools, or your teammates do, keep one source of truth. Put the content in `AGENTS.md`, and make `CLAUDE.md` a one-line import that Claude Code understands:

```md
@AGENTS.md
```

Now both agents read the same rules.
</Explain>

<Interview q="How do you get an AI coding agent to follow your team's conventions?">
Put the conventions where the agent reads them every session: a short instructions file at the repo root (CLAUDE.md or AGENTS.md). Keep it to rules that are specific and checkable, like commands, file layout, test-first, and things never to do. Then back the important rules with something deterministic: tests, a linter, a typecheck in CI or a hook. Instructions steer the agent; checks catch it when it drifts. I review the file like code, because a vague rule costs context every session and still gets ignored.
</Interview>

<Interview q="Agents forget everything between sessions. How do you work with that?">
I treat the repo as the memory. Decisions go into the instructions file, ADRs and the spec; progress goes into commits and a short task list. A new session starts by reading those, so it doesn't depend on a chat history. I also keep sessions small: one task per session, with the plan written down, so nothing important lives only in the context window.
</Interview>
