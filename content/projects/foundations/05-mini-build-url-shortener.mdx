<Pitfall
  id="pitfall-ip-behind-proxy"
  title="rate-limits everyone together once it's deployed"
  recovery={`On the host, every request comes through a proxy, so req.socket.remoteAddress is the proxy's IP and all users share one bucket. Read the client IP from the first value of the x-forwarded-for header when it's present, fall back to remoteAddress, and add a test for both cases. Only trust x-forwarded-for because our host sets it; note that in a comment.`}
>
It works on your machine and breaks in production, which is exactly why you deploy early. Most hosts put a proxy in front of your process.
</Pitfall>

<Explain id="deploy">
Now deploy. shortly is a long-running Node process, so pick a host that runs one: Render, Railway and Fly.io all have free or low-cost tiers. The steps are the same everywhere:

1. Connect your GitHub repo.
2. Build command: `pnpm install`. Start command: `pnpm start`.
3. The host sets `PORT`; your server already reads it.
4. Set the health check path to `/health`.

Remember: the store is in memory, so links disappear on every deploy. That's fine for now, and it's in your spec's out-of-scope list.
</Explain>

<Interview q="Design a URL shortener. What changes when it has to handle a lot of traffic?">
Start with the core: generate a short unique code, store code to URL, redirect with a 301 or 302. Reads vastly outnumber writes, so the redirect path should hit a cache, like Redis or the CDN, before the database. Codes come from random bytes with a uniqueness check, or from a counter encoded in base62 if I need them short and collision-free across nodes. Rate-limit creation per user or IP at the edge, validate URLs, and block abusive targets. Analytics should be counted asynchronously so the redirect stays fast.
</Interview>

<Interview q="Why use a token bucket for rate limiting, and where does the state live when you run more than one server?">
A token bucket allows short bursts up to the bucket size while enforcing an average rate, which matches how real clients behave. On one process, the state can live in memory, which is what shortly does. With multiple instances, each would have its own buckets and the real limit would multiply, so the state moves to a shared store like Redis, using an atomic increment or a small Lua script so concurrent requests can't both take the last token.
</Interview>
