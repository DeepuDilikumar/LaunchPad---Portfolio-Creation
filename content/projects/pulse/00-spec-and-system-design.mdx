<Explain id="intro">
Pulse is a real-time messenger: 1:1 and group chat, presence, typing indicators, delivery and read receipts, offline sync and media. By module 9 it will hold thousands of concurrent connections under a load test.

Before any code, you'll do what a senior engineer does on day one of a new system: write down what it does, what it doesn't, and how the pieces fit. The agent is a fast, tireless partner for this. It's also very willing to design a system for a billion users when you need one for a thousand. Your job is to keep it honest.
</Explain>

<Explain id="what-makes-chat-hard">
Chat looks simple and isn't. The hard parts, which you'll meet one module at a time:

- **Ordering.** Two people send at the same moment, from different servers. Everyone must see the same order.
- **Exactly-once, from the user's point of view.** Phones retry on bad networks. A retry must never show a message twice.
- **Fan-out.** One message to a 200-person group is 200 deliveries, to users connected to different servers.
- **Presence.** "Online" is a guess built from heartbeats. Get it wrong and people flicker on and off.
- **Offline.** A phone that was in a tunnel for ten minutes has to catch up, in order, without missing anything.
</Explain>

Now cut. Read the PRD's requirements and ask of each one: *does v1 need this to demonstrate the hard parts?* Good v1 non-goals for Pulse:

- End-to-end encryption (a big topic of its own; mention it as future work)
- Voice and video calls
- Message editing and reactions
- Federation or bots
- Groups over 256 members

Fewer features, built properly, make a far better portfolio piece than many features built shallowly.

<Explain id="message-path">
Check the agent's message path against this one. Every step should be in its document:

1. The client creates a **client ID** (a UUID) for the message and sends it over the socket.
2. The gateway checks the sender is a member of the conversation.
3. In one database statement, the gateway assigns the next **sequence number** for that conversation and inserts the message. A retry with the same client ID returns the original message instead of creating a new one.
4. The gateway acknowledges the sender with the sequence number: the "sent" tick.
5. The gateway publishes the message to a Redis channel for the conversation.
6. Every gateway node with a member connected receives it and pushes it down those sockets.
7. Each recipient's client acknowledges: the "delivered" tick.

Ordering is decided in step 3, by the database, not by anyone's clock.
</Explain>

<Explain id="adrs">
An **ADR** (architecture decision record) is a short file that captures one decision: the context, the options, what you chose and the consequences. They're how a team remembers *why*. They're also excellent interview material, because they're your reasoning, written down at the time.

Write two now:

- **ADR 0001:** WebSockets vs Server-Sent Events vs long polling for real-time delivery.
- **ADR 0002:** How messages are ordered (sequence numbers vs timestamps).
</Explain>

<Callout id="interview-design" kind="interview">
"Design WhatsApp" or "design Slack" is one of the most common system design questions. You'll answer it from experience: you'll have built the ordering, fan-out and presence yourself, with numbers from your own load test.
</Callout>

<Interview q="Design a chat system for 1:1 and group messages. How do you guarantee message order?">
I'd order per conversation, not globally. When the server accepts a message, it assigns the next sequence number for that conversation inside the same database write, for example by incrementing a counter on the conversation row and inserting the message in one statement, so the database serialises concurrent sends. Clients render and sync by sequence number, never by timestamps, because clocks skew between servers and devices. If a client sees seq 41 then 43, it knows it missed 42 and fetches it.
</Interview>

<Interview q="Why WebSockets instead of polling or Server-Sent Events for chat?">
Chat is bidirectional and latency-sensitive: clients send messages, typing events and acks constantly, and receive pushes. WebSockets give one persistent full-duplex connection for both. SSE is server-to-client only, so sends need separate HTTP requests; that's workable, but typing and acks get chatty. Long polling adds latency and overhead per message. The cost of WebSockets is stateful connections: you need sticky routing or a pub/sub layer between nodes, and you have to handle reconnects. For chat that trade-off is worth it.
</Interview>
