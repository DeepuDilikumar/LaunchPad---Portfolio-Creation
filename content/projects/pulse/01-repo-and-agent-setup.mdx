<Explain id="intro">
A good repo setup is invisible. Commands are obvious, the agent knows the conventions, and CI catches mistakes before they land. A bad one costs you a little on every single session for the rest of the project.

In this module you'll scaffold Pulse as a small monorepo: a web client, a WebSocket gateway and a shared package for the types both sides agree on. No features yet. Just a skeleton where `pnpm test` and CI are green from the first commit.
</Explain>

<Explain id="why-monorepo">
Why one repo with three packages instead of three repos?

- **One source of truth for the protocol.** The message types the client sends and the gateway accepts live in `packages/shared`. Change a field and both sides fail to compile until they agree.
- **One agent session can see everything.** The agent can follow a message from the client into the gateway without you pasting code between repos.
- **One CI pipeline.** Every change is tested against both sides.

The cost is a little workspace tooling. pnpm workspaces keep that small.
</Explain>

<Explain id="protocol">
The one piece of real code in this module is the protocol. Every message on the socket is a JSON object with a `type`, validated with zod on the way in. Unknown or malformed messages are rejected, never trusted. Starting with `ping` makes the whole path testable before chat exists.
</Explain>

<Expect id="protocol-example" kind="diff" example>

```ts
import { z } from "zod";

export const ClientMessage = z.discriminatedUnion("type", [
  z.object({ type: z.literal("ping"), id: z.string().uuid() }),
]);
export type ClientMessage = z.infer<typeof ClientMessage>;

export const ServerMessage = z.discriminatedUnion("type", [
  z.object({ type: z.literal("pong"), id: z.string().uuid() }),
  z.object({ type: z.literal("error"), code: z.string(), message: z.string() }),
]);
export type ServerMessage = z.infer<typeof ServerMessage>;
```

</Expect>

<Explain id="ci-and-hooks">
Two guardrails before any feature:

- **CI** runs typecheck and tests for the whole workspace on every push and pull request.
- **A pre-commit hook** runs the same checks locally, so a red commit never leaves your machine. Keep it fast; the full suite can stay in CI if it gets slow.
</Explain>

<Decision id="decision-repo" question="What did you decide to put in packages/shared, and what did you deliberately keep out of it?" />

<Interview q="How would you structure a codebase where a web client and a real-time server share a protocol?">
A monorepo with a shared package that owns the protocol: message types defined once, as runtime schemas like zod, so both sides get static types and the server can validate untrusted input at runtime. The client and server import from it, so a protocol change breaks compilation on both sides until they agree. I'd version messages with a type field and add new types rather than change existing ones, so old clients keep working during a deploy.
</Interview>

<Interview q="What do you put in CI on day one of a project, before there are features?">
Install with a frozen lockfile, typecheck, and the test suite, even if there's one test. The point is that the pipeline exists and is green, so every later change is measured against it. It also proves the build works on a clean machine, not only mine. Lint and formatting come next; slower stages like end-to-end tests and load tests come later, once there's something to test.
</Interview>
